## 2024-06-18 - Prevent Server-Side Request Forgery via baseUrl parameters
**Vulnerability:** The AI Gateway orchestrator (`fetchOpenAICompatible`) and model fetchers dynamically set request targets based on the user-provided `baseUrl`. This allowed potential SSRF attacks where a user could provide internal URLs (e.g., `http://169.254.169.254/latest/meta-data`) to access cloud metadata endpoints or probe the internal network.
**Learning:** We need to explicitly validate any URLs provided via input before resolving and fetching them, especially because the service routes dynamic AI endpoints. Basic protocol validation (`http`/`https`) is insufficient without DNS resolution and IP range checking to prevent internal network scanning.
**Prevention:** Implement a central utility (`validateSafeUrl` in `server/security.ts`) that performs DNS lookup on user-provided hostnames and rejects IPs mapping to private, link-local, broadcast, or reserved networks. We deliberately allow loopback (e.g. `127.0.0.1` and `localhost`) specifically to support legitimate local AI providers like Ollama. Ensure this utility is applied to `req.baseUrl` fields prior to dispatching any fetch requests. To avoid TOCTOU/DNS rebinding, full protection would require the fetch to explicitly use the resolved IP alongside proper SNI/Host headers.

*Update*: A vital missing component of early SSRF fixes involves `fetch` mechanics in Node.js. Since `fetch` auto-follows redirects up to 20 times by default, an attacker can supply an externally valid URL that returns an HTTP `302 Found` redirecting to `169.254.169.254`. This completely bypasses the initial input validation. **Prevention:** Always include `redirect: 'error'` or `redirect: 'manual'` in fetch configs alongside the input validation layer.
